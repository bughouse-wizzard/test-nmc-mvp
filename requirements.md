Ниже — детальное ТЗ на MVP без авторизации, но с полным рабочим воркфлоу: поиск контрактов по КТРУ + параметрам, парсинг/скачивание/анализ документов состоявшихся закупок, скоринг соответствия и расчёт НМЦК, а также интерфейс строго по макету фронт13.html и сценарию из задания . В конце добавил большой раздел “как парсить zakupki.gov.ru” максимально пошагово “для junior”.
1) Цель MVP и границы
Цель
Автоматизировать рутинный процесс определения НМЦК на основе 3 найденных контрактов (приоритет — идентичные, иначе однородные) по правилам, описанным в задании :
·	пользователь задаёт КТРУ, параметры (44-ФЗ, статус исполнения, регион заказчика, период 3 года, лимит контрактов и т.д.),
·	система находит контракты в реестре контрактов ЕИС,
·	по каждому контракту вытягивает спецификацию “Платежи и объекты закупки” и/или вложения (“Печатная форма” для 2025+) ,
·	сравнивает характеристики с ТЗ,
·	делает AI-скоринг соответствия,
·	даёт пользователю таблицу результатов + выбранные 3 контракта сверху и рассчитанную НМЦК .
Вне MVP (осознанно не делаем)
·	Авторизация/роли/права.
·	Массовая параллельная обработка “на всю страну” (делаем безопасный лимит и очередь).
·	Юридически значимые отчёты “по форме приказа” (делаем JSON/CSV/XLSX + “читаемый отчёт”, но без претензии на регламент).
2) Пользовательские сценарии (User Stories)
1.	Ручной запуск поиска
·	В боковой панели “Новый поиск” пользователь вводит:
o	Наименование объекта, КТРУ (ОКПД2), производитель (опционально), округ/регион, период, лимит контрактов, текст характеристик .
·	Нажимает “Начать поиск”.
·	В “Истории поисков” появляется запись со статусом “В работе” и кнопкой “Остановить” .
·	После завершения — статус “Завершен”, число найденных, средняя цена, доступен переход в “Результаты”.
1.	Запуск поиска из файла ТЗ
·	Пользователь загружает doc/docx/pdf/html, выбирает позицию/лот, система автозаполняет часть полей (КТРУ, имя, ключевые характеристики), как в макете .
1.	Просмотр результатов + выбор 3 контрактов
·	Таблица результатов: ссылка на контракт, номер, год, цена за единицу, тип совпадения (идентичный/однородный), производитель (и предупреждение для 2025+), AI Score, кнопка “Сравнение” (модалка) .
·	Галочки: выбранные (по умолчанию топ-3 по скорингу) закрепляются сверху.
·	НМЦК = средняя/агрегированная цена по выбранным (в MVP: среднее; расширение: медиана/с отсечением выбросов).
1.	Остановка поиска
·	Кнопка “Остановить” прекращает текущую обработку и фиксирует статус “Остановлен” .
3) Функциональные требования (что именно должно работать)
3.1. Модуль “Поиск контрактов”
Фильтры должны соответствовать заданию :
·	Закон: 44-ФЗ
·	Статус: “Исполнение завершено” и “Исполнение прекращено”
·	Регион/округ заказчика: MVP — СЗФО (дальше расширяем)
·	Дата заключения: 3 года от текущей даты
·	Объект закупки: код позиции КТРУ (укрупненная позиция) + при необходимости текст
·	Лимит обработки контрактов: по умолчанию 30 (настраиваемо)
Выход поиска:
·	found_total — число найденных контрактов “как на сайте”
·	contracts[] — список карточек (реестровый номер, дата, цена контракта, заказчик, ссылки)
3.2. Модуль “Парсинг карточки контракта”
Для каждого контракта:
·	Получить базовые поля:
o	ссылка вида ...contractCard/common-info.html?reestrNumber=...
o	реестровый номер
o	дата заключения
o	цена контракта / при наличии — цена за единицу (если структурировано)
·	Перейти во вкладку “Платежи и объекты закупки” и извлечь спецификацию (позиции + характеристики)
·	Вложения:
o	для контрактов 2025+ скачать “Печатная форма” и извлечь: КТРУ, наименование, характеристики, производитель (если указан)
Важно про источники данных: с 1 января 2025 доступ к FTP, по описаниям, закрывается и предлагаются сервисы отдачи данных/документов по SOAP; для некоторых режимов может потребоваться токен/ЭЦП (Habr). В MVP предусматриваем 2 стратегии: (а) аккуратный web-парсинг публичных страниц; (б) “коннектор документов” через сервис отдачи (если заказчик даст токен).
3.3. Модуль “Сопоставление характеристик (match engine)”
Вход:
·	target_specs — нормализованные требования из ТЗ (или из текстового поля)
·	contract_specs — нормализованные характеристики из контракта/печатной формы
Выход:
·	match_type: Идентичный / Однородный
·	diff_log: список совпадений/расхождений по каждой характеристике
·	manufacturer_check:
o	если в контракте найден производитель и он != целевому — пометка
o	для 202ерка производителя выполнена / совпало / нет”
MVP-правил“работало”):
·	Нормализация:
o	lower, trim, замена “,” на “.” для чисел
o	выделение чисел+единиц (“80 г/м2”, “160%”, “500 мл”)
o	словарь синонимов для частых параметров (плотность/граммаж, белизна/CIE и т.п.)
·	Совпадение:
o	точное для чисел+единиц (с допускаемым “± допуск”, если указан)
o	fuzzy по строкам (Levenshtein/rapidfuzz) для названий
·	Классификация:
o	“Идентичный”, если совпали “основные признаки” (набор обязательных полей)
o	“Однородный”, если совпало >= X% ключевых и нет критических конфликтов
3.4. AI-скоринг и аналитика (ИИ-агент)
ИИ используется для:
·	извлечения характеристик из неструктурного текста ТЗ,
·	извлечения характеристик из “печатной формы”/pdf/docx,
·	объяснения, почему контракт “подходит/не подходит”,
·	итогового скоринга 0–100 и рекомендации “в расчёт / не в расчёт”.
Требования:
·	AI должен возвращать строго JSON по схеме (см. ниже), чтобы фронт работал стабильно.
·	Все “сырые” ответы и промпты логируются (для дебага).

5) Архитектура MVP (рекомендовано)
Компоненты
1.	Frontend: статический SPA (как макет) + API вызовы.
2.	Backend API (REST + SSE/WebSocket):
o	управление поисками (создать/остановить/статус),
o	выдача истории,
o	выдача результатов,
o	выгрузка отчёта.
1.	Worker/Queue (внутри backend или отдельный процесс):
o	делает поиск,
o	парсит контракты,
o	скачивает вложения,
o	вызывает AI,
o	пишет результаты в БД.
1.	Storage:
o	PostgreSQL (поиски, контракты, характеристики, логи),
o	файловое хранилище (локально/S3-совместимое) для вложений и отчётов.
Почему очередь нужна даже в MVP
Чтобы работали:
·	кнопка “Остановить”,
·	лимиты,
·	стабильный прогресс,
·	повторяемость.

9) План работ (итерации MVP)
Итерация A — “скелет + UI”
·	Поднять backend + БД.
·	Подключить фронт фронт13.html как основной UI .
·	Реализов запуск, остановка, прогресс, мок-результаты (как сейчас в html).
Итерация B — “реальный поиск контрактов”
·	Реальный запрос в реестр контрактов: получение found_total и списка карточек.
·	Ограничение лимитом и сортировка “сначала свежие” .
·	Сохраненя C — “парсинг карточки и спецификации”
·	Парсер карточки контракта (общая инфо + “платежи и объекты закупки”).
·	Скачивание вложений.
·	Извлечение цены за единицу (если доступно).
Итерация D — “ИИ-скоринг + выбор 3 + НМЦК”
·	DeepSeek интеграция через config.
·	Сравнение характеристик + модалка “Сравнение”.
·	Автовыбор top-3, расчёт НМЦК, экспорт отчёта.
Итерация E — “устойчивость”
·	Кэширование, ретраи, лимиты запросов.
·	Логи, трассировка, дедупликация скачанных документов.
10) Большой раздел: как парсить zakupki.gov.ru (подробно для junior)
10.1. С чего начать: правила и ограничения
1.	Соблюдай robots.txt. Для zakupki.gov.ru в robots встречается Crawl-delay: 60 (то есть 1 запрос/60 сек для “*”) (zakupki.gov.ru).
→ Для MVP делай очередь и редкий темп, иначе рискуешь блокировками.
2.	Не делай “взлом”: только публичные страницы, без обхода ограничений.
3.	Всегда ставь:
o	понятный User-Agent,
o	таймауты,
o	ретраи с backoff,
o	сохранение “сырых ответов” для дебага.
10.2. Что именно парсим (публичный поток)
Точка входа реестра контрактов:
·	страница поиска: /epz/contract/search/search.html (zakupki.gov.ru)
·	страница результатов: /epz/contract/search/results.html (zakupki.gov.ru)
Карточка контракта открывается ссылкой вида:
·	/epz/contract/contractCard/common-info.html?reestrNumber=...
10.3. Алгоритм “поиска контрактов” (junior-friendly)
Шаг 1. Собери параметры поиска (то, что ввёл пользователь)
Из ТЗ: 44-ФЗ, статус исполнения, округ, 3 года, КТРУ, лимит .
Шаг 2. Сформируа практике сайт передаёт фильтры query-параметрами (пример с ktruCodeNameList встречается в URL результатов) (zakupki.gov.ru).
В MVP подход:
·	сначала открыть страницу поиска тров (через DevTools Network),
·	затем воспроизводить GET запрос к results.html?....
Шаг 3. Скачай HTML результатов
·	GET https://zakupki.gov.ru/epz/contract/search/results.html?...
Шаг 4. Вытащи:
·	число найденных записей (текст “более … записей”)
·	список карточек:
o	реестровый номер,
o	дата заключения,
o	ссылка “Карточка контракта”
o	цена контракта
(эти поля видны в результатах поиска) (zakupki.gov.ru)
Шаг 5. Отсортируй “сначала свежие”
В задании сказано: “в первую очередь обрабатываются наиболее свежие” .
Если сайт даёт сортировку параметром — используй её; иначе сортируй по дате из HTML.
Шаг 6. Обрежь до limit_contracts (по умолчанию 30) .
10.4. Алгоритм “парсинга карточки контракта”
Шаг 1. Открой common-info
·	GET .../contractCard/common-info.html?reestrNumber=XXXX
Шаг 2. Спарси базовые поля (HTML)
·	номер, даты, цена, заказчик и т.д.
Шаг 3. Найди вкладкуъекты закупки”
В задании прямо сказано: туда нужно переходить, чтобы открыть спецификацию и характеристики .
Технически это обычно другая страница/роут внутри contractCard. Делается так:
·	смотри ссылки в меню карточки,
·	либо через Network найди запрос, который подгружает “объекты закупки”.
**Шфикацию
·	наименование позиции,
·	КТРУ/ОКПД2 (если отображается),
·	количество, цена за единицу,
·	блок характеристик под позицией .
Шаг 5. Для 2025+ скачай “Печатную форму”
В задании: “Для контрактов от вложения скачивается файл ‘Печатная форма’…” .
Значит нужно:
·	открыть вкладку “Вложения”,
·	найти ссылку на файл,
·	скачать в storage,
·	распарсить текст (pdf/docx) → отдать в AI экстрактор.
10.5. “Официальный” путь документов (альтернатива/усиление)
Есть подход через сервисы отдачи информации/документов (SOAP). В писывается, что после 1 января 2025 доступ к FTP закрывается и предлагают SOAP-сервисы; для части сценариев могут потребоваться токены/ЭЦП (Habr)ктичный вывод для MVP**:
·	делаем web-парсинг публичных страниц как основной,
·	но сразу проектируем “DocumentProvider” интерфейс:
o	WebAttachmentsProvider (скачивание с вкладки “Вложения”),
o	SoapDocsProvider (если заказчик даст токен; в конфиге).
10.6. Типичные ошибки junior и как их избежать
1.	Парсим только results.html и думаем, что “цена за единицу” там есть — обычно нет, она в спецификации.
2.	Не сохраняем сырой HTML/док → потом невозможно понять, почему парсер сломался.
3.	Нет лимитов/ретраев → бан/ошибки/падения.
4.	Характеристики сравнивают строка-в-строку → нужно нормализовать числа/единицы и использовать fuzzy.
11) Формат отчёта (обязательный выход)
По требованию :
·	сохраняем “данные сверки соответствия каждого контракта” в файл отчёта
